## ISSUE-023 Windows 卡顿、同步失败与 HTTP 500 无法追踪

- 对应需求：RQ-017-H（原始专项文档编号 RQ-015，与既有编号冲突后顺延）
- 状态：🔴 有问题
- 问题：Windows 页面和操作卡顿，项目同步偶发失败，接口偶发 HTTP 500；旧版本没有 requestId、结构化异常堆栈和扫描指标，历史 500 无法还原到具体异常。
- RQ-017-HA 诊断结论：
  1. **首要架构瓶颈**：`run-windows-api.bat` 把 `POINT_QUOTE_DATA_DIR` 指向共享盘工具目录，运行 SQLite 仍在 SMB 上；数据库锁、日志、知识库读写都可能争用同一网络共享。
2. **同步全量扫描过多（旧行为）**：此前所有写请求以及项目/品牌读取都会运行 `knowledge_repository.sync()`；一次写操作可能在业务处理前后各同步一次。同步会枚举品牌和项目 Markdown，并逐项目比对快照。RQ-017-HE 已使只读请求及数据库型项目/报价修改走本机缓存，并将知识库写回改为延迟同步；直接操作产品/品牌笔记和共享附件的文件请求仍可能等待共享文件 I/O。
  3. **产品库重复扫描（旧行为）**：此前产品列表、单项查找和保存前查找均通过 `PRODUCT_DIR.rglob("*.md")` 递归扫描；保存产品时 `_find()` 可能重复扫描。RQ-017-HE 已将产品列表改为复用 30 秒进程索引，过期索引由后台线程刷新；点位创建和报价 ID 映射只查内存目录，不在相应请求路径扫描或 stat SMB。
  4. **首页重复同步**：首屏同时请求项目、品牌、产品和类型；项目与品牌请求分别触发同步，项目/品牌数量变化后又请求同步状态，再触发一轮同步。
  5. **高频保存存在**：点位名称、房间、数量、图标大小、颜色和摄像头角度使用 `onChange` 直接 PATCH，文字输入可逐字符触发；每个 PATCH 又带来前后两轮知识库同步。多选拖动在松手后虽只提交一次，但会按点位串行发送多个 PATCH。
  6. **报价重复写入**：报价已有 700ms 防抖，但打开服务费设置时每个 `SystemFee` 的初始化 effect 都会提交一次未修改数据，造成多组不必要请求。
  7. **500 具体来源**：旧中间件在业务接口执行前直接同步知识库，`PermissionError`、Windows 文件占用、SMB 超时、`os.replace` 失败、SQLite `locked/busy/disk I/O` 都会未经分类直接成为 500；知识库 `_atomic_write()` 只有一次 replace，没有临时占用重试。
  8. **并发风险**：FastAPI 可并行处理多个请求，但目前没有按 filePath 的写锁；不同请求可能同时覆盖同一项目 Markdown。产品写入虽有短重试，最终回退为删除旧文件再重命名，过程中存在短暂文件缺口。
  9. **watcher 结论**：项目代码没有文件 watcher，因此当前不存在“自身写入→watcher→再次写入”的循环；卡顿不是 watcher 导致。
  10. **路径结论**：Windows 启动脚本使用原生绝对路径和 `%~dp0`/`%%~fI`，中文与映射盘基本可用；尚无统一路径层，`smb://`、`file://` 不是业务路径输入。UNC 是否在目标 Windows/NAS 组合稳定仍需实机验证。
- 性能基线（2026-09-30，SMB、采样时 4 个项目/14 个品牌/约 15 个有效产品，macOS 只读测量）：项目列表平均 530.5ms，产品列表 90.2ms，打开项目 138.4ms，同步状态 179.7ms。加入诊断后，正式运行日志的一次项目列表请求耗时 483.93ms，并在同一 requestId 下多轮扫描产品目录，证实项目列表为每个报价产品递归查找。RQ-017-HC 已加入按文件元数据缓存和产品 ID 索引；更新后的正式业务数据未在本机服务上重测，Windows 实机延迟仍需实测。
- 已完成的最小修改：A 阶段加入本机 JSONL 诊断日志、请求 ID、错误分类、完整堆栈、知识库扫描/写入指标、5MB 日志轮换和只读诊断状态接口；B 阶段加入 800ms 保存合并、手动冲刷待保存报价、同文件串行锁、相同内容去重、临时文件双重校验、有限重试和 Windows/NAS 备份换位回滚。未改变业务规则、报价算法或正式数据。

### RQ-017-HE｜2026-09-30 Windows / Mac 点位与页面交互性能

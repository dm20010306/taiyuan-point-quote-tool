## 1. 文档关系

- 本文档是长期保留的总蓝图，记录完整目标、路线和各阶段开发提示词。
- `REQUIREMENTS.md` 是当前有效需求与验收标准的唯一入口。
- `ISSUES.md` 记录问题、原因、解决方案、测试结果和后续问题。
- `CHANGELOG.md` 记录每次实际修改的文件、影响范围和验证结果。

每次开发前先阅读上述三个活文档；完成后必须同步更新。本文档不代替活文档。

## 4. 详细需求

### RQ-001 产品分类体系重构

状态：🟢 已解决

原问题是“产品分类、设备点位、所属系统”概念重叠。最终规则：

- 设备点位：决定产品对应图纸中的哪种设备。
- 所属系统：决定报价时产品进入哪个系统。
- 旧“产品分类”停止作为新业务分类使用；如旧字段仍存在，应保留兼容，不破坏历史数据。

### RQ-002 网络点位拆分与非智能区域

状态：⚪ 待开发

1. 原“网络”点位拆成“吸顶 AP”和“墙面 AP”，产品库的设备点位字段同步支持；所属系统仍为“网络系统”。
2. 新增“非智能区域”图纸工具，采用类似调光区域的框选交互，但使用明显不同的半透明填充、描边和标签。
3. 非智能区域可移动、缩放、删除。
4. 非智能区域不是产品，不进入产品库、不计数、不报价。
5. 必须兼容历史“网络”点位，不能直接破坏旧项目。

### RQ-003A 开关添加前选择产品

状态：⚪ 待开发

- 点击“开关”后先选择具体产品；候选只显示“设备点位 = 开关”的产品。
- 选择后进入连续布点模式，可一次放置多个相同产品点位。
- 点位必须保存稳定的 `productId`，不能只保存产品名称。
- Esc、右键或切换工具退出连续添加模式。
- 验收包括新增、删除、移动、保存、重新打开后的产品关联。

### RQ-003B 区域与点位点击冲突

状态：⚪ 待开发

- 最终点击优先级必须为：设备点位 > 区域。
- 点击区域内设备时选中设备；只有点击区域空白处才选中区域。
- 调光区域与非智能区域采用相同规则。
- 应修改真实的 hit-test / pointer event / selection priority 逻辑，而不是只改视觉层级。
- 选择、拖动、删除、右键和属性编辑都遵循同一优先级。

### RQ-003C 窗帘方向可视化

状态：⚪ 待开发

- 第一版只支持“单电机 + 单方向”。
- 鼠标按下、拖动、松开生成 `■────────→`；起点方块代表电机，终点箭头代表方向。
- 属性增加“显示电机”，默认开启；关闭后隐藏方块，但保留方向线与箭头。
- 移动、旋转、调整、保存和重新打开后，电机、线、箭头关系不得丢失。
- 第一版不开发双电机/双开帘。

### RQ-003D 摄像头监控范围

状态：⚪ 待开发

- 采用放置时拖动决定方向的方案 A。
- 图形由摄像头、两条边界线和半透明扇形组成。
- 支持方向、扇形角度、距离、整体旋转；摄像头移动和删除时范围同步更新。
- 保存并重开项目后监控范围正确恢复。
- 第一版仅用于图纸表达，不做真实焦距与监控距离计算。

### RQ-004 项目“已签”状态

状态：⚪ 待开发

- 首页项目卡片增加“已签”勾选。
- 勾选后使用克制的浅绿色或品牌强调色，并显示小型“已签”标签。
- 状态持久保存，重开应用不丢失。
- 本阶段不扩展“施工、完工”等其他状态。

### RQ-005 进货价隐蔽模式

状态：🔵 待优化

- 保留现有进货价数据和算法。
- 移除明显文字入口，只在固定角落保留极淡、无文字的小区域。
- 双击该区域开启，再次双击关闭。
- 开启后只出现价格数字，不显示“进货价、成本价、成本”等文字，表头也不出现相关字样。
- 关闭后整列消失；每次首次打开默认隐藏，以客户展示安全优先。

### RQ-006 品牌 Logo 库

状态：⚪ 待开发

- 品牌至少包含：品牌 ID、中文名、英文名、别名、Logo、启用状态、备注。
- Logo 优先 SVG，其次透明 PNG；产品通过 `brandId` 关联，不重复保存 Logo。
- 产品库可显示 Logo 或 Logo + 名称；报价品牌列优先只显示 Logo，无 Logo 时回退到文字。
- 建议容器：`max-width: 42px; max-height: 18px; object-fit: contain;`，禁止拉伸、裁剪和变形。
- 支持新增、编辑、上传、更换、删除 Logo、启用/停用和别名匹配。
- 必须验证网页报价与 PDF 导出的比例、位置一致。

### RQ-007 问题、版本、解决方案记录体系

状态：🟡 开发中

STEP 0 已完成文档部分：建立总蓝图、`REQUIREMENTS.md`、`ISSUES.md`、`CHANGELOG.md`。

后续帮助页升级规划：

1. 保留现有系统简介、快速使用、快捷键、版本记录与问题反馈表单。
2. 将“版本记录”区域升级为“开发与问题中心”。
3. 顶部显示五个低饱和状态统计卡：已解决、开发中、待优化、待开发、有问题。
4. 支持按状态筛选需求与问题卡片。
5. 每张卡至少显示编号、标题、问题/需求、原因、解决方案、状态、版本、测试结果、新问题和更新时间。
6. “需求与问题”回答“还有什么需要处理”；“版本历史”回答“某版本实际修改了什么”，两者分开展示。
7. 页面数据应来自单一、可维护的数据源；实现阶段先检查现有技术结构，再决定使用前端常量、后端接口或数据库，避免 Markdown 与页面形成两套无同步规则的数据源。

页面升级不属于本次文档任务，实施时应作为 RQ-007 的独立小步开发和验证。

## 6. 固定开发规则

每次只处理一个指定 RQ，并遵循：

1. 开发前阅读 `docs/REQUIREMENTS.md`、`docs/ISSUES.md`、`docs/CHANGELOG.md`。
2. 不重构无关代码，不更换技术栈，不改变无关 UI。
3. 优先复用组件，优先兼容旧数据，不删除历史数据。
4. 涉及数据结构时写清迁移和回退方案。
5. 完成后执行与风险匹配的测试，并检查相关模块回归。
6. 同步更新三个活文档和帮助页状态（页面功能完成后）。
7. 未完全验证不得标为“已解决”；新缺陷应新建 ISSUE，不塞进原需求含糊带过。
